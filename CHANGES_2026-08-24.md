# Changes — 2026-08-24: the migration chain was never actually working

## Summary

While investigating why the dashboard's notes feature couldn't be verified
against Postgres, I installed a real Postgres instance in the sandbox and
ran the actual Alembic migration chain against a genuinely fresh database
for the first time. Migration 0001 — the very first one — failed
immediately:

    RuntimeError: RLS table customers has no tenant_id column

This is not a notes-specific issue. Migrations `0001`, `0002`, `0004`,
`0005`, `0007`–`0015` all reference a `tenant_id` column and a `tenants`
table that stopped existing in the ORM models (`models/core.py`) once the
app was refactored to the owner/location model. Nothing after migration
0001 could ever run on a fresh database. This had been invisible because:

- The original `predeploy.py` (before the 2026-08-22 fix) never called
  Alembic at all — only the raw bootstrap.
- `run_alembic_migrations()` silently swallows any exception unless
  `RAILWAY_ENVIRONMENT`/`FLASK_ENV`/`APP_ENV` is set — so it fails loudly on
  real Railway, but silently everywhere else, including this sandbox's
  earlier SQLite-only testing.
- The SQLite boot smoke tests (`tests/test_boot_smoke.py`) never exercise
  Alembic at all — `run_alembic_migrations()` only runs when the backend
  is postgresql.

**Verified fixed**: the complete 20-migration chain now runs successfully,
twice in a row (idempotent), against a real, freshly created Postgres 16
database installed in this sandbox specifically to test this. New
`tests/test_postgres_migration_chain.py` runs the same check automatically
wherever a Postgres instance is available (skips gracefully otherwise, so
it can't break SQLite-only CI).

## Every fix in this pass

**`migrations/versions/0001_phase2_foundation.py`** — the fail-fast check
and RLS setup rewritten to use `location_id` instead of `tenant_id`.
Removed the 4 `flyer_lady_*` table names from its scan list — they're
created by a later migration (0011) and aren't ORM models, so checking
them here raised `KeyError` before the RLS loop could even run.

**`migrations/versions/0002_paystack_phase3.py`** — `tenant_id` → `location_id`.

**`migrations/versions/0004_service_rules_phase5.py`** — `tenant_id` →
`location_id`, plus two independent bugs found while testing it for real:
the default seed rows were gated on "table didn't already exist," which
became permanently false once `service_rules` became an ORM model created
by 0001 — meaning the 4 generic maintenance rules never got seeded on any
fresh deploy. Fixed the gate to check row count instead. Then found the
`active`/`created_at`/`updated_at` columns only have Python-side ORM
defaults, which a raw `bulk_insert` bypasses — added explicit values.

**`migrations/versions/0005, 0007, 0008, 0009`** — `tenant_id`/`tenants` →
`location_id`/`locations` in both the DDL and RLS policy text. Mostly
unreachable in the normal fresh-chain case (their tables are ORM-managed
and already exist by the time these run, so their own `if table already
exists: return` guard skips the broken code) but fixed for correctness in
any partial-chain or historical-database scenario.

**`migrations/versions/0010_post_service_review_phase18.py`** — this one
matters more than the others in this "probably dead code" group: it was
altering a `tenants` table that never exists, but the columns it adds
(`review_platform`, `review_url`, etc.) are NOT already on the raw
bootstrap's `locations` table, and ORM `create_all()` silently skips
tables that already exist — so this migration is the only mechanism that
actually adds them. Fixed to target `locations`.

**`migrations/versions/0011_flyer_lady_social_publishing.py`** — the real,
load-bearing fix in this group. `flyer_lady_specials`,
`flyer_lady_special_approvals`, `flyer_lady_special_posts`,
`flyer_lady_public_links`, `flyer_lady_link_clicks` are not ORM models —
this migration is the only place they're created, with real `tenant_id`
FKs to the nonexistent `tenants` table. Fixed to use `location_id` FKs to
`locations`.

**`migrations/versions/0012, 0013, 0014`** — these "repair RLS" migrations
gate their work on `"tenant_id" in columns`; fixed to check `location_id`
instead (otherwise they'd silently no-op forever once the tables they
target use location_id, quietly dropping RLS coverage those tables depend
on them for).

**`migrations/versions/0015_subject_notes.py`** — the notes table itself:
`tenant_id` FK to `tenants` → `location_id` FK to `locations`; RLS policy
now checks `app.location_id`, matching what the app actually sets.

**`migrations/versions/0018_meta_location_ownership.py`** — unrelated to
the tenant_id issue: tried to add two unique constraints already declared
on the ORM model and created by 0001, causing
`psycopg2.errors.DuplicateTable` on a fresh chain. Added existence guards.

**`migrations/env.py`** — Alembic's own `alembic_version.version_num`
column is hardcoded to `VARCHAR(32)`; this project's revision IDs exceed
that (`0009_booking_confirmation_phase15` is 34 characters), which failed
the first version-stamp write once the chain reached one. Widened it via a
separate, fully autocommitted connection *before* Alembic opens its own
migration connection — an earlier attempt that mixed the raw DDL into
Alembic's own connection caused the entire migration run to silently roll
back (everything Alembic did, including `alembic_version` itself,
vanished with no error) — a genuinely nasty failure mode to debug, worth
noting in case this code is touched again.

**`ai/dashboard/queries.py`** — `booking_notes()` used
`subject_id = ANY(:vehicle_ids)`, which is Postgres-only syntax (fails on
SQLite) — rewritten to use SQLAlchemy's portable expanding `IN` bind
parameter instead.

**`phanta_app.py`** — separate bug, found while verifying the dashboard
end-to-end against real Postgres for the first time: `current_user` is
referenced directly in `templates/base.html` and
`templates/dashboard/workshop.html` (`current_user.get('email')`, `{% if
current_user %}`), but nothing ever injected it into the Jinja template
context — no `context_processor` existed anywhere, and `render_template()`
calls don't pass it individually. Flask's default lenient `Undefined`
silently no-ops `{% if current_user %}`, which is why this stayed hidden,
but `workshop.html`'s first line calls `.get()` on it directly, which
raises and 500s the whole dashboard. Added an `@app.context_processor`
injecting `current_user()` globally.

## Verified, end to end, against real Postgres in this session

1. Fresh database → `python -m database.predeploy` → all 20 migrations
   succeed → `alembic_version` correctly at `0020_automation_location_ownership`.
2. Re-running predeploy against the now-migrated database is a clean no-op
   (idempotent).
3. `notes` table exists with `location_id NOT NULL REFERENCES locations(id)`
   and its RLS policy checks `app.location_id`.
4. Seeded the demo workshop, logged in as the reception account, hit
   `/dashboard` — 200, no error, correct "3 bookings today" reflecting the
   real seeded data, confirming the notes query (previously untestable
   against Postgres) now executes cleanly as part of that page.
5. Full existing test suite: 198 passed, 5 skipped (3 pre-existing
   Postgres-only skips + 2 new ones from this pass), 0 failed — no
   regressions from any of the above.
