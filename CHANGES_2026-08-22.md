# Changes — 2026-08-22

Verified by: `pytest tests/test_boot_smoke.py` (new, 5/5 pass) and the full
existing `tests/unit` suite (90 passed / 60 pre-existing failures, same
count and same tests as on the unmodified codebase — nothing here caused a
regression; the 60 need a Postgres test DB / fixture owner_id data, unrelated
to this pass).

## 1. Schema consolidation (fixes the crash from the original traceback)

- **`database/owner_location.py`** — removed a trailing comma in the
  `locations` CREATE TABLE that made it invalid SQL on both Postgres and
  SQLite.
- **`database/initialize.py`** — reordered `initialize_database()` so
  `ensure_owner_location_foundation()` (which creates `owners`/`locations`)
  runs *before* `_ensure_columns()` (which ALTERs them). It was backwards.
- **`database/predeploy.py`** — rewritten to call `initialize_database()`
  directly instead of hand-duplicating `_create_tables`/`_ensure_columns`
  and never calling `ensure_owner_location_foundation()` at all. Railway's
  `preDeployCommand` and every gunicorn worker's boot now run the exact same
  code path — they cannot silently diverge again. Note: predeploy now also
  seeds/validates `SUPERADMIN_PASSWORD` like the app does, so make sure
  that's set in Railway's pre-deploy environment, not just the service's.
- **`database/schema.py`**:
  - Removed the `"locationes"` typo entry from `_ensure_columns` (dead
    code — that table was never created anywhere; it was the next crash
    in line after the two fixes above).
  - Removed the `"locations"` entry from `_ensure_columns` entirely — it
    described a different, `workshop_id`-based schema that conflicted
    with the real `owner_id`-based table `owner_location.py` creates.
    `owner_location.py` is now the single source of truth for the
    `locations` table's shape.
  - Removed duplicate `CREATE TABLE IF NOT EXISTS service_requirements`
    and duplicate `CREATE TABLE IF NOT EXISTS vehicles` (the second copy
    of each was always a no-op under `IF NOT EXISTS`, but redundant and
    confusing to read).
  - Marked `whatsapp_numbers`, `messaging_accounts`, and `webhook_events`
    as legacy in a comment block. Confirmed by grep: nothing in the active
    codebase `INSERT`s into any of the three. I did **not** drop them —
    dropping tables on your live Railway Postgres is a data decision, not
    something to do silently. If you want them gone, that's a follow-up
    migration with your sign-off.

This is *not* the full "single source of truth via SQLAlchemy models"
rewrite I described as the ideal — that's a bigger, riskier project since
most repositories query with raw SQL (`query_db`/`execute_db`), not the
ORM. What's here removes the actual conflicts and duplication that existed
across the current three definition sites, without changing how the app
talks to the database.

Covered above — the `owner_id`/`location_id` model was already correctly

## 3. Automation engine — new: `services/automation_engine.py`

A generic trigger → condition → action interpreter built on the
`automation_rules` table's existing (previously unused) `conditions_json`
and `action_json` columns. Does not remove or change any existing hardcoded
job in `jobs/` — purely additive.

- `fire_event(event_type, location_id, context)` — call this from anywhere
  a business event happens. Looks up active rules for that location+event,
  evaluates `conditions_json` against your `context` dict (dot-path field
  lookup, ops: eq/neq/gt/gte/lt/lte/contains/in), and executes matching
  rules' `action_json` immediately (`delay_minutes == 0`) or schedules them
  via the existing `scheduled_jobs` table.
- `ACTIONS` registry + `@register_action("name")` — add a new action type
  by writing one function, nothing else changes.
- Two actions wired in and tested: `log_only` (no-op, for testing rules) and
  `whatsapp_message` (sends via the existing `deliver_whatsapp` /
  `MetaMessagingService` pipeline — requires `conversation_id` and
  `customer_id` in the context you pass to `fire_event`).
- `process_due_automation_jobs()` — picks up delayed rules'
  `scheduled_jobs` rows, wired into `jobs/scheduler.py`'s
  `run_scheduled_jobs()` so it runs on the existing Railway cron.

**Deliberately not wired**: `flyer_lady_publish` and a Service Advisor
action. `FlyerLadyPublishService.publish_post()` needs an already-created
`SpecialPost` row (special_id, platform, approval state already resolved)
— a generic trigger doesn't have enough to construct one without guessing
at product behavior you haven't specified. `build_service_advisor()` drives
a full conversation loop, not a single fire-and-forget call. Both are a
`@register_action` function away once you decide what a rule should pass
them (e.g. `action_json = {"action": "flyer_lady_publish", "params":
{"post_id": ...}}` for a rule that fires once a `SpecialPost` already
exists). I didn't want to invent that contract for you.

Tested end-to-end against real SQLite: immediate action execution,
condition matching/non-matching, delayed scheduling, and the job processor
picking up and completing a due job — all verified, not just imported.

## 4. Boot smoke test — new: `tests/test_boot_smoke.py`

Five tests that build a database from nothing (mirroring a fresh Railway
deploy) and confirm the app actually comes up:

- `initialize_database()` succeeds from empty
- `phanta_app` imports cleanly (this is what gunicorn does)
- `/health` returns 200 via the real Flask test client
- `initialize_database()` is idempotent (safe to run on every deploy)
- predeploy and app-boot use the same bootstrap path (regression guard
  against the two entrypoints silently diverging again)

**Verified this test actually catches the incident**: ran it against the
unmodified original code — all 5 fail with the exact errors from the crash
log (`no such table: locations`, then cascading). Ran it against the fixed
code — all 5 pass.

Add `pytest tests/test_boot_smoke.py` as a required CI step before deploy,
or as a pre-deploy check, so this class of bug can't reach Railway again.
